# GET.ride — Flutter

Flutter client for **GET.ride** that runs on **web, desktop (macOS / Windows / Linux), iOS and Android** from one codebase. It talks to the **same Supabase project** as the Expo app in [getgroupmy/get.ride](https://github.com/getgroupmy/get.ride), so accounts, rides, wallets and support chats are shared between both apps. The backend itself — schema, migrations, seed data and edge functions — lives in [`supabase/`](supabase) in this repository (moved from get.ride); see [docs/backend.md](docs/backend.md).

## Features

| Area | What works |
| --- | --- |
| Sign-in | Phone number → SMS OTP → 6-digit PIN. A device whose public IP is on the admin's blacklist (`ip_access_rules`, Expo `IpAccessContext`) is told "Service Not Available" and cannot sign in, book or go online; checks fail open. Expo's whitelist PIN bypass for admins is deliberately not ported. Returning users sign in with their PIN. Same contract as the Expo app (`profile_phone_lookup`, `verify_pin_for_login`, `set_login_pin`, PIN-derived Auth password), so a PIN set in either app works in both. A new account can enter a friend's referral code on the set-PIN step (pre-filled from an invite link's `ref`); `apply_referral` credits both accounts' bonus GET.coin, and a refused code never holds up the sign-up. |
| Ride booking | OpenStreetMap map, place search, choose-on-map, route + ETA, TEKSI fare calculation (ported from `utils/maps.ts`) priced on the admin's fare-AI traffic estimate when the `ai-route-proxy` edge function gives one (provider keys stay server-side; estimated tolls shown, not added to the fare), else on the map route, service + payment choice, creates `ride_requests` rows and pings partners via the `send-push` edge function. |
| Ride tracking | Live status via Supabase Realtime, driver details + live position, trip code, call/SMS driver, cancel / cancellation-request flow. **Fare bidding**: while the request is open the rider can raise the fare (+RM1/5/10, capped at 4× the first quote, which clears any standing bid and pushes partners), and where the admin's region settings allow bidding (`offer_me`, Expo `useRegionBidding`: mapped boundary first, then country/state/city names) a partner's counter-offer appears as a card to accept or decline. Accepting moves the rider's own row to `accepted` with that partner, billed at the offer, matched on the exact partner and amount shown. |
| Trip receipts | Finished trips in the trip list open a receipt (Expo `ride-detail`) read from the stored request, so it can be reopened any time: a stable booking number (`GR-` + the id, where Expo invented a random one on each open), route with pickup and drop-off times, trip time, distance, the driver (or, on the driver's copy, the passenger) and vehicle, payment mode, and the trip fare plus any tolls / other charges on the row. A cancelled or expired request shows no charge and the reason. **Print**, **Share PDF** (`printing` + `pdf`, every platform) and **Copy** as text. |
| Change phone number | Settings → Change phone number (Expo `change-number`): the new number is checked against other accounts (`profile_phone_lookup`), Supabase Auth texts a code to it (`auth.updateUser`), and the change takes effect once the code is entered (`verifyOTP` type `phoneChange`). The PIN is unchanged. `profiles.phone` follows through migration 0092 (`sync_profile_phone`); before it is applied the profile keeps the old number. |
| Partner onboarding | From the Drive tab: profile photo, ID number (+ optional ID photo), address, service area, partner type, then the required documents for those types and areas, submitted for admin review (Expo `partner-onboarding`). Resumes at the first missing step; rejected or expired documents can be uploaded again from the submitted application. The partner row is claimed (`claim_partner_by_phone`) or created as an unapproved stub, within the 0088 guards. |
| Vehicle onboarding | Drive → My vehicles: each vehicle's review status or the step it stopped at, and Add vehicle. Plate, make & model (Settings → Vehicle Make & Model), year & colour, four photos, owner ("my own vehicle" fills it from the partner), then the vehicle's documents, submitted for review (Expo `vehicle-onboarding`). A plate the partner already has resumes; a plate on another account says so instead of failing (partners can only read their own vehicles, so it cannot be claimed from the app). Documents tagged with the **Vehicle** document type are uploaded per vehicle (`vehicle_documents`) and left out of partner onboarding. |
| Meter Digital (first slice) | The in-app taxi meter for TEKSI partners (speedometer icon on the Drive tab, route `/meter`; Expo `meter-digital`). Meters on **GPS** at 1 Hz (displacement between trustworthy fixes, ground speed as the fallback, jitter and jumps filtered), billed on the operator's rate card from `meter_digital_settings`, resolved off the first fix's geography (suburb → city → state → country → global → built-in TEKSI tariff) and frozen for the life of a hire. DAY / NIGHT keys (preselected from the card's night window), EXTRA keys, START / PAUSE / RESUME / END. END stops the fare at once and opens a declaration that cannot be dismissed: passengers, luggage, tolls & charges and airport (with its surcharge); RESUME HIRE restarts from now. Hires go to a device-local trip log with receipts (copyable text). A running hire cannot be walked out of. Engine, declaration, record and receipt are pure and tested (`core/taxi_meter.dart`, `core/meter_trip.dart`). |
| OBD-II reader (Wi-Fi, Bluetooth LE) | Settings for a Wi-Fi or Bluetooth LE ELM327 dongle (the meter's app-bar button, route `/meter/reader`; Expo `obd2-reader`): add, select, connect and remove readers (kept on the device); a Bluetooth reader is found with an in-app scan (a BLE dongle never shows in the phone's own Bluetooth list), filtered to likely OBD-II dongles with a show-all switch, with live status, protocol and readings. One shared session (`data/obd/obd_session.dart`) keeps the link up and reconnects every 4 s; the meter joins it rather than opening its own. The meter bills on the vehicle speed (PID 0D) while it is fresh and falls back to GPS where the rate card allows it; a GPS-only card never uses the reader, and an OBD-only card needs a live reader to start. The odometer (PID A6) is read before the fare opens and again after END, and both ends print on the receipt. Wi-Fi uses plain Dart sockets; Bluetooth uses `universal_ble` (BSD-3; chosen over `flutter_blue_plus`, whose 2.x licence needs a paid commercial licence) and tries the FFF0, HM-10 (FFE0) and Nordic UART serial profiles before a generic writable + notifiable fallback. A browser cannot connect. Protocol, adapter book and client are pure and tested (`core/obd.dart`, `core/obd_adapters.dart`, `core/obd_ble.dart`, `data/obd/obd_client.dart`). |
| Vehicle information | What the linked OBD-II reader can tell about the car (the meter's car button or the reader screen, route `/meter/vehicle`; Expo `vehicle-information`): odometer, fuel level and an estimated distance to empty (OBD-II publishes neither tank size nor range, so it is worked out from the tank size the driver enters and a consumption figure — measured from this car's own burn once it has covered 20 km, else live fuel rate or MAF, else the entered average — and the card names which); identity (VIN decoded, calibration IDs, ECU name); stored / pending / permanent trouble codes; readiness monitors; every mode-01 parameter the car lists, decoded through a ~70-entry catalogue; and the adapter. The scan borrows the shared reader session with the 1 Hz sweep paused. Writes are the four Expo has (clear codes, set protocol, reset reader, raw command), each behind a warning; ECU writes are refused while the car is moving, re-checked when confirmed. Pure logic: `core/obd_pid_catalog.dart`, `vehicle_info.dart`, `vehicle_scan.dart`, `fuel_range.dart`. |
| Receipt printer (Bluetooth LE, Wi-Fi) | Mini thermal (ESC/POS) printers for Meter Digital (the meter's printer button, route `/meter/printer`; Expo `meter-printer`): add a Bluetooth LE printer found with an in-app scan (a mini printer never shows in the phone's own Bluetooth list) or a Wi-Fi printer by IP (port 9100 by default), with its paper width (58 mm / 80 mm), select it, run a test print and reprint the last receipt; kept on the device. The receipt's **Print** button sends it straight to the selected printer with no print dialog (a job is connect, write, close); with none set up it offers the setup screen, and the receipt can still be copied as text. The ESC/POS document is plain ASCII built from the same lines as the on-screen receipt, so paper and phone never disagree. Wi-Fi uses plain Dart sockets. Bluetooth uses `universal_ble`: a known print service first (18F0/2AF1 and four others), else the first writable characteristic outside the standard services, write-without-response preferred, streamed in packets sized to the negotiated MTU (capped at 180 bytes, 15 ms apart). Every Bluetooth device gets its own command queue, so a receipt streaming to the printer never holds up the OBD-II reader's commands. A browser cannot print. Renderer and printer book are pure and tested (`core/escpos.dart`, `core/printers.dart`). |
| Landscape console | Meter Digital is read off a dash mount, so the console is landscape: the device is pinned to landscape while the meter is in front, and rotation goes back to the app default on leaving it or opening its printer / reader settings (and is re-pinned on return or when the app comes back to the foreground). Where the platform will not turn (a browser, an iPad in split view, a rotation lock) the console is turned a quarter turn instead, safe-area insets included, and its dialogs and the end-of-hire form live in a navigator inside that stage so they turn with it. The console is one fixed instrument laid out at 820 wide and scaled to fit, so it never scrolls, and it ignores the OS font scale. Meter / Trip log tabs sit on a side rail; back from the trip log returns to the meter. Geometry is pure and tested (`core/landscape_stage.dart`). |
| Book TEKSI EV | The customer's nine-step electric-car order (Account → Book TEKSI EV, route `/ev`; Expo `teksi-ev`): model (custom build or an in-stock unit) → specification (colours, wheels, accessories; a stock unit's wheels can be swapped and are flagged for a re-fit) → order fee → owner (self / someone else / company, ID details typed, optional ID photo) → plate (transfer or new) → financing (cash, hire purchase, leasing, rental plans from the admin catalogue) → delivery advisor (assigned by the back office, or linked with the advisor's DA code) → delivery date (3–17 days out) → handover checklist, which the customer accepts to complete the order. Catalogues come from the `ev_*` tables; the order lives in `ev_orders` (owner-scoped) and is resumed on any later visit. **Nothing is charged in the app**: the order fee, a cash balance and a leasing add-on are recorded as due, and Admin → EV Orders marks each one received (Expo's card/FPX form charged nothing yet recorded them paid). Unlike Expo, the ID card is not sent to a third-party AI to be read, itemised taxes are counted, delivery dates use the local calendar, and changing the finance type clears the old plan. The logic is pure and tested (`core/ev_wizard.dart`, shared with the back office's `ev_orders.dart`). |
| Meter auto-launch | A rate card's **Open the meter on launch** switch (`auto_launch`, set in Admin → Meter Digital) makes Meter Digital the landing screen for TEKSI partners cleared to drive: on sign-in and on every relaunch the home screen opens the meter. Decided once per sign-in, so leaving the meter for the passenger side is never undone, and never while a ride is in progress (as rider or partner). The card is the one for where the meter last ran (kept on the device), else the global card; the rate cards are cached on the device so the decision, and the meter's pricing, work offline. Lookups give up after 10 s and the driver stays home. Off by default. The rule is pure and tested (`core/meter_auto_launch.dart`). |
| Drive (partner) | Online toggle, live queue of open requests sorted by distance, race-safe accept, **Auto-accept** (takes each request that arrives while it is on, nearest first, never one already queued when it was switched on) and **Allow OfferMe requests** (off: rider's price only, no counter-offer), as on Expo's e-hailing console, **Offer price** on requests open to bidding (presets of +20/30/50 %; the partner waits up to 45 s for the rider, sees whether they won, were outbid, declined or the fare was raised, and the offer is withdrawn if no answer comes), arrive → verify trip code → start → complete, live location publishing, commission charged via `wallet_charge_ride_commission` (rate resolution ported from `utils/commissionStore.ts`). |
| Driver permit | For TEKSI partners, Drive → the permit badge (Expo `partner-teksi` permit card, `utils/driverPermitSource.ts`): the permit is the upload for the required document tagged *Taxi Driver Permit display* (`isTaxiPermit`), else one the AI check read as a taxi permit, never an unrelated upload. Fields come from the AI-read permit, then the upload's own columns, then the partner / profile; a missing photo stays empty (Expo showed a stock photo of a stranger). Shows review status and expiry (warns within 30 days), and holds **Meter Digital** behind Expo's Start Pickup checks: the permit IC must match the profile, the permit must not have expired, and the vehicle being driven must be the permit's. Pure and tested in `core/driver_permit.dart`. |
| AI document checks | Picking a document photo (partner onboarding, vehicle documents, admin uploads) sends it to the `document-ai-verify` edge function (`supabase/functions/document-ai-verify`), which asks the vision provider the admin configured for fare AI, with the keys kept on the server, whether it is a real document of the requested type, and reads its number, dates, insurer and PWD flag. The verdict is shown in the upload dialog, only blank fields are filled in, and it is saved with the document (`ai_verification`, `ai_verified`, `issuance_country`, `detected_document_name`) in the same shape Expo stores. It never blocks an upload: without a verdict an admin reviews it as before. Unlike Expo, no photo is sent from the phone to a third party. |
| Shared vehicles (co-drivers) | A vehicle can be driven by its owner plus drivers and co-drivers an admin adds on the vehicle's page (Admin → Vehicles → edit → Drivers: by phone number, pause/resume, remove, end the current session). Drivers choose their car on the Drive tab (the **Vehicle** card lists owned and assigned cars with their role and state) and **Hand back** frees it for the next driver; only one driver uses a vehicle at a time, enforced by the `claim_vehicle` / `release_vehicle` RPCs (`vehicle_user_assignment` / `vehicle_active_session`). Expo has the flow but no admin screen. |
| Wallet | GET.wallet / GET.coin / credit balances and the latest transactions. **History** pages through the ledger a month at a time (this month and the five before it) with wallet tabs (GET.credit for partners), category chips (Ride, Reward, Referral, Transfer, Reload, Refund, Other), day groups and a details sheet per row, labelled the same way as Expo's `walletDisplay.ts`. **Trade GET.coin** buys and sells coins against GET.wallet at the admin rate. With market pricing on, it shows a buy price of max(market, peg) and a sell price of min(market, peg), read from the `get_coin_trade_quote` RPC (migration 0089) or worked out on the device from the rate model shared with the admin GET.coin screen. Trades settle only through the `wallet_trade_coins` RPC, which prices the trade itself and re-checks the balances and the supply cap server-side. **Send** asks another account (phone number or wallet ID) to accept GET.coin: the recipient gets an approval card over whatever screen they are on, the sender waits with the option to withdraw, and coins move only on acceptance (`wallet_request_coin_transfer` / `wallet_respond_coin_transfer`, 15-minute expiry). **QR**: Receive shows the account's `getpay://u/<id>` code (optionally with a fixed amount, valid for 60 s) and GET.coin QR shows the same code with the wallet ID. **Scan & Pay** opens the camera (or takes a pasted code). A GET account's code opens Send addressed to that account, so the person on the code is the one credited. Any other code is a QR payment out of GET.wallet, optionally part-paid with GET.coin, through the `wallet_pay` RPC, which debits the payer only. **Recharge GET.credit** (partners): moves money from GET.wallet to GET.credit, which pays commissions, through the owner-scoped `wallet_recharge_credit` RPC; an amount over the GET.wallet balance is refused before the call. **Ride rewards**: when a trip completes, the rider's tracking panel (and the trip receipt, for a ride that finished while the app was closed) claims the ride's GET.coin reward through `wallet_award_ride_coins`, which is idempotent per ride and, from migration 0093, prices the reward on the ride's stored fare rather than the one the app sends. |
| VoiceProtection | A switch in Settings (per account, kept on the phone). With it on, the driver's phone records trip audio from Start trip to the end of the ride (mono AAC, `record` package) into the app's private folder; the trip screen shows a recording indicator. Files are never played back to the user and are deleted after 24 hours. Each recording gets a `voice_protection_recordings` row; a support agent asks for one from the ticket chat (Admin → Support → ticket → Trip audio), the phone that holds it uploads it to the private `voice-protection` bucket, and the agent plays it from a one-hour signed link. Phones only: a browser or desktop build neither records nor answers requests. |
| Push notifications | Android and iOS, through Firebase Cloud Messaging. The token is stored with the same `push_register_token` RPC as the Expo app, and the `send-push` edge function delivers to both kinds of token. Taps open the partner queue (ride requests) or the wallet (GET.coin transfers). Needs a Firebase project (see below and `docs/store-release.md`); a build without one has no push. |
| Safety | Account → Safety (Expo `safety.tsx`): emergency contacts summary, VoiceProtection and **Emergency SOS**, which opens Messages to every emergency contact with a map link to the rider's position (Expo's text promised the location but never sent it). During a ride, **SOS · Emergency** offers calling 999 or alerting contacts with the location, driver and car. |
| Session & location tracking | Every launch, sign-in and return to the app writes a `user_sessions` row (device, app version, and the public IP / ISP / city from the `ip-lookup` edge function), and while signed in a `user_location_history` row is written at least every 30 s, or after moving 10 m (no closer than 5 s apart). These feed Admin → Session History and the fraud screens, which saw only Expo devices before (Expo `SessionTrackingContext`). Location permission is asked once; everything is best-effort and never blocks the app. Logic in `core/session_telemetry.dart` and `data/session_tracker.dart`. Unlike Expo it does not read carrier name / MCC / cellular generation, which need native plugins. |
| Admin display switches | The rider app honours the Admin → Display switches that change behaviour (Expo `DisplaySettingsContext`): **Service enabled** off makes booking show "This service isn't available yet" instead of placing a request; **Registration enabled** off refuses sign-up to a number with no account (existing accounts still sign in); **Show AI toll charges** off hides the toll estimate on the booking panel. Unreadable settings keep the defaults, so the service never switches off by accident. Expo's pixel offsets, side-menu layout and vehicle-bar order are for Expo's own screens and have no Flutter equivalent. Logic in `core/app_display.dart`. |
| Rules & terms | Settings → Rules & terms (Expo `rules-terms.tsx`, whose three rows did nothing): Terms and conditions and Privacy Policy open in the browser, Licenses lists the bundled open-source packages. The phone screen links the same two pages. Addresses: `--dart-define=TERMS_URL=…` / `PRIVACY_URL=…` (defaults `https://getride.my/terms-of-service`, `https://getride.my/privacy`). Expo's intro and passenger/driver screens are not ported: the role chosen there was never stored or used. |
| Navigation app | Settings → Navigation app: Google Maps, Waze, or Apple Maps on iPhone/Mac. The driver's **Navigate** button on a trip opens the chosen app (its https link opens the installed app, or the web version when it is missing). Kept on the device. Expo's `navigation.tsx` offered the same choice but never saved or used it; its language and distance-unit screens did the same and are not ported (the app is English and kilometres only). |
| Recent destinations | The place picker lists the rider's recent drop-offs (newest first, one per place, their own bookings only) until they start typing; how many follows Admin → Display → Recent Locations (on/off and count 0–8). Expo's home-screen "recent locations" were eight fixed Klang Valley malls, the same for every rider. Logic in `core/recent_places.dart`. |
| Destination mode | On the Drive tab while online: set where you are heading (home, end of shift) and switch it on. Requests whose trip brings you at least 2 km closer, and is mostly progress rather than detour, are listed first and marked **Toward your destination**; auto-accept takes only those. Kept on the device. Expo's `partner-ehailing.tsx` had the toggle ("Prioritising requests toward destination") but never changed the queue; its airport-area filter only served that picker and is not ported. Logic in `core/destination_mode.dart`. |
| User guide | Account → User guide: how each part of this app works (getting started, riding, trips, wallet, driving, TEKSI meter, safety, account), searchable. Written for this app; Expo's `user-guide.tsx` described Expo's screens, including features neither app has (promo codes, intro slides). Content in `core/user_guide.dart` — keep it in step when a feature changes. |
| Account | Profile edit (with a profile photo, uploaded to the account's own folder in the `avatars` bucket and saved on `profiles.avatar_url`), **Invite friends** (the account's referral code, its getride.my/?ref= link and invite text to copy, how many friends joined with it, and who invited this account, through `get_my_referrer`), emergency contacts, support chat (realtime), light/dark theme, change PIN. |
| Layout | Bottom navigation on phones, navigation rail on tablets, extended rail + side-by-side map panels on desktop/web. |

Not ported yet (still Expo-only): MFi / USB OBD-II readers, Bluetooth classic receipt printers.

## Admin panel (`lib/src/admin/`, route `/admin`)

Opened from **Account → Admin panel**, which only appears for accounts with at least one `admin_access` row. Access comes from the database only: the same rows `caller_is_admin()` checks in every RLS policy. There is no local admin password, unlike the Expo panel's hardcoded login. Page keys are the Expo route keys (`admin-users`, `admin-settings-promocode`, …, `*` for everything), so grants made in either app apply to both. On a brand-new project the first signed-in user can claim admin through `admin_access_bootstrap()`.

| Module | What it does |
| --- | --- |
| Dashboard | Live counts (users, partners awaiting approval, open/active rides, documents to review, open tickets), each linking to its list. |
| Users | Search and filter (approved / unapproved / ID failed / blocked / rejected / deleted), details, set account status. |
| Partners / Vehicles | Search and filter including permit states, details, set status, set permit, mark documents complete. |
| Documents | Partner and vehicle documents: review queue, open front/back files, AI verification details, approve or reject with notes. Expiry is shown as `Expired`. |
| Rides | Monitor open, in-progress, completed and cancelled requests, view full details, cancel a ride. |
| Support | Ticket pool (active / unassigned / mine / resolved), realtime chat as admin, assign to me, change status. |
| Push notifications | Broadcast to everyone, passengers or partners via `send-push`, plus send history. |
| Commission rates | Create, edit and delete master/country/state/city/suburb/user rules. |
| Settings | All 23 Expo CRUD categories, generated from the Expo screens into `admin_categories.g.dart`, including the insurance provider → type → duration → premium drill-down and ordering. Any other `settings_entries` category gets an advanced raw-JSON editor. |
| Sub-admins | Grant per-page read/edit access by phone number, revoke grants. |

Every other Expo admin screen is ported under `/admin/m/…` and listed on the **Settings** hub by section (`lib/src/admin/screens/<group>/`):

| Section | Screens |
| --- | --- |
| People | Add/edit partners and vehicles (photos, documents, service areas), edit users, user ID-document review |
| Services & catalogue | Services, vehicle services, partner types (icons), document types, required documents, vehicle makes & models, service assignment |
| Payments & commerce | Payment types, payment gateways (public fields only; see security notes), GET.coin, EV order fee / finance options / vehicle details / inventory, EV orders back office |
| Geography | Countries/states/cities with geofences, airport areas, multi-gate places and gates (OpenStreetMap search and polygon editing) |
| Meter & app | Meter Digital rate cards (scoped, live panel switches), display and mock settings, site, app icon, splash, always-on pages |
| Security & integrations | Session history with trails/heatmap, fraud tracing, IP access rules, API keys (masked), eLife, fare AI and its logs, read-only backend diagnostics |

Intentionally not ported: user *add* (a profile needs an auth account), Rork chat (Expo/Rork-specific, ships a toolkit secret), the Expo backend screen's runtime URL/service-role-key entry, installed-app detection, and any client-side handling of secrets.

## Deploy (web → Vercel)

Production is **https://getride.my**. `www.getride.my` redirects there, and `getride-snowy.vercel.app` is the project's own Vercel address for the same deployment. Both domains are attached in the Vercel project (Settings → Domains), so no workflow names them: every production deploy is served on them automatically. The privacy policy is a plain static page, `web/privacy.html`, served at https://getride.my/privacy; the apps and the store listings link to it.

Deploying is the last step of CI. Every push to `main` whose `flutter analyze` and tests pass (`.github/workflows/flutter.yml`) runs `.github/workflows/deploy-web.yml`, which builds the web app and uploads it to Vercel **production**. Other branches and pull requests get the checks only: the team is on Vercel's free plan (100 deployments a day, shared with every project on the team), and per-branch previews used that up. Running *Deploy web* by hand on another branch still makes a preview. Vercel has no Flutter builder, so the site is built in GitHub Actions and shipped prebuilt (`vercel deploy --prebuilt`); every unknown path falls back to `index.html` so deep links reach the router. It can also be run by hand from the Actions tab (*Deploy web*).

The only credential is the `VERCEL_TOKEN` repository secret. The team and project ids (`team_EBG91tunYkCckYh5bCELGRU3`, `prj_P1tZDFvZfEFMT7z84MtAVd1sa80b`) are identifiers, so they are written into the workflow; a `VERCEL_ORG_ID` / `VERCEL_PROJECT_ID` secret or variable overrides them. Vercel's own Git deployments should stay off for the project (Settings → Git), since they cannot build Flutter and would publish an empty site.

Web Analytics and Speed Insights are wired into `web/index.html` as Vercel's script tags (the non-npm forms of `@vercel/analytics` and `@vercel/speed-insights`); turn each on in the project's **Analytics** / **Speed Insights** tab and it starts reporting from the next deploy. The web app uses real path URLs (`/rides`, not `/#/rides`; `usePathUrlStrategy()` in `lib/main.dart`), so Analytics reports each screen separately; old `/#/…` links are rewritten to their path on load.

Until all three are set, the workflow skips the deploy and leaves a notice instead of failing. It can also be run by hand from the Actions tab (**Run workflow**), which deploys `main` to production and any other branch as a preview.

## Release (App Store / Google Play)

The iOS and Android apps ship as **`com.taxxee.teksi`**, the same store listings the Expo app used. Admin → Settings → **App Release** (in this admin or the Expo one) starts `.github/workflows/ios-release.yml` / `android-release.yml` through the `ios-release` / `android-release` Supabase edge functions, which build, sign and upload. The workflows skip with a notice until their secrets exist. Setup, version-number offsets and the shared upload key are in [`docs/store-release.md`](docs/store-release.md).

## Layout

```
lib/
  main.dart
  src/
    config.dart          build-time configuration
    app.dart             theme + router (auth redirects)
    providers.dart       Riverpod providers
    core/                pure logic ported from the Expo app (auth, fare, commission, formatting)
    data/                Supabase repositories, models, geocoding/routing
    features/            auth, ride, partner, wallet, profile, support, settings, shell
    widgets/             shared widgets (map, empty states, code field)
test/                    unit + widget tests
```
