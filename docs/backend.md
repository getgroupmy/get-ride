# Backend (Supabase)

The database schema, migrations, seed data, edge functions and their tests live
in [`supabase/`](../supabase). They moved here from `getgroupmy/get.ride`, the
Expo app's repository, when the Expo app was retired; their history up to the
move is in that repository.

Both apps were written against this one backend, so the notes below — carried
over from get.ride's `CLAUDE.md` — still name Expo files (`utils/…`, `app/…`,
`contexts/…`) where they describe client behaviour. Those paths are in the
archived Expo app; the Flutter equivalents are under `lib/src/`.

## Working on it

```bash
./supabase/check-migration-numbers.sh   # CI runs this on every PR
deno test supabase/functions            # edge-function unit tests (CI too)
supabase db push                        # run by a person after merge, never automatically
supabase functions deploy <name> --no-verify-jwt
```

New tables/columns: update `supabase/schema.sql` **and** add the next numbered
migration (one higher than the highest on `main`). See
[`supabase/README.md`](../supabase/README.md) → Deploying migrations.

## Database notes

The full, consolidated schema lives in `supabase/schema.sql` (idempotent — safe to re-run). Key tables: `profiles`, `partners`, `vehicles`, `partner_documents`, `settings_entries`, `app_settings`, `rides`, `ride_requests`, `wallets`/`wallet_transactions`, `commission_rates`, `meter_digital_settings`, `support_tickets`/`support_messages`/`support_calls`, `push_tokens`, `push_notifications`, `ip_access_rules`, plus geo tables (`countries`/`states`/`cities`/`suburbs`/`airport_areas`).

`supabase/migrations/` holds the numbered migrations, starting from `0097_squashed_baseline.sql` (a copy of `schema.sql` at the time of the squash, which replaced the old `0001`–`0097` chain because preview branches and `supabase db reset` replay the folder from an empty database and that chain could not do it); the replaced files are kept in `supabase/migrations_archive/` for history. `schema.sql` is the canonical full snapshot. CI's Migrations replay job builds a fresh database from the folder and runs `supabase/tests/*.sql`. When adding tables/columns, update `schema.sql` and add a new numbered migration. Use the next number after the highest on `main`, and re-check after merging `main` into your branch: `supabase/check-migration-numbers.sh` (run by CI) fails on a reused version or a misnamed file. The Supabase CLI takes the digits before `_` as the version; the four duplicate pairs from before the check (now in the archive) had their second file suffixed (`00241_`, `00421_`, `00641_`, `00891_`). Migrations reach the live project with `supabase db push` (`supabase/config.toml`; run by a person after merge, never automatically), not by pasting into the SQL editor, which leaves the CLI's history out of step. `supabase/baseline-migration-history.sh` lines that history up with the folder and verifies the result (done on the live project on 2026-10-05, and needed once more after the squash, see the README; `setup.sh` runs it on new ones). See `supabase/README.md` → Deploying migrations.

`supabase/functions/` holds Deno edge functions. There are three: `send-push` fans a notification out to the registered device tokens using the service-role key and logs to `push_notifications`. It sends only for the database webhook, the service-role key or a signed-in admin (see Ride Dispatch below) — Expo push tokens (`ExponentPushToken[…]`, the Expo app) through Expo's push service, and Firebase Cloud Messaging tokens (the Flutter app in getgroupmy/get-ride) through the FCM HTTP v1 API, authenticated by the `FCM_SERVICE_ACCOUNT` function secret (the Firebase project's service-account JSON; without it FCM devices count as failed and Expo devices are still sent to). Token classification, the FCM message shape and which FCM errors prune a token are pure and tested in `_shared/push.ts` / `push_test.ts`; `ip-lookup` resolves the caller's public IP and ISP/geolocation (the mobile client can only see its LAN IP); `ai-route-proxy` runs the fare-AI route estimation (provider/key failover loop from `utils/geminiRoute.ts`) server-side — it reads the `fare_ai_provider` settings row with the service-role key so the provider API keys never reach the client, and logs attempts to `fare_ai_responses`/`fare_ai_key_states` exactly like the client used to. `geminiRoute.ts` calls the proxy first and only falls back to the legacy client-side loop when the function isn't deployed. `document-ai-verify` is the AI check of a partner's uploaded document photos for both apps: it accepts only a signed-in caller (the user's access token is verified with `auth.getUser`), sends the base64 images to the vision provider from that same `fare_ai_provider` row (optional `documentProvider` / `documentModels.<provider>` overrides, `documentChecksEnabled: false` to switch it off; text-only providers answer `provider_no_vision`), stores nothing, and answers the same `DocumentAiVerificationResult` shape the Expo client normalises in `utils/documentAiResult.ts` — prompt, request shapes and normalisation are pure and tested in `_shared/doc_ai.ts` / `doc_ai_test.ts`. It only reads `fare_ai_key_states` (skips keys fare AI has cooling down) and never writes it, so a failed image call cannot take a key away from fares. The Expo app calls it through `verifyDocumentWithAi` (`utils/documentAiVerify.ts`; hosted images are downloaded and inlined first, since the function only accepts data URLs); any failure, including the function not being deployed (a 404), is simply no result, so ID photos never go to a third party the admin didn't configure. Nothing in the app calls Rork's `toolkit.rork.com` any more: the old fallback, the edit-profile / TEKSI EV ID-card reading and the two-selfie "liveness" check (all of which sent photos there) and the admin Rork AI chat were removed — ID number and address are typed in, and the profile photo is a single selfie. Rork remains only as the dev tooling (`bunx rork start`, `withRorkMetro`). Normalisation and that response rule are pure and tested in `utils/documentAiResult.ts`. Deploy with `supabase functions deploy <name> --no-verify-jwt`.

`turn-credentials` hands a signed-in caller the ICE servers for a support call (migration `0105`): STUN, plus short-lived TURN relay credentials in the TURN REST API form coturn checks without a user table (username `<expiry>:<user id>`, password base64(HMAC-SHA1(secret, username)), valid 6 hours). Secrets: `TURN_URLS` (comma list of `turn:`/`turns:` URLs) and `TURN_SECRET` (coturn's `static-auth-secret`, `use-auth-secret` mode), optional `STUN_URLS`; without the TURN pair it answers STUN only, and calls connect only where a direct connection does (not on many mobile networks). The credential maths is pure and tested in `_shared/turn.ts` / `turn_test.ts`. Unlike the functions above it is deployed **with** JWT verification (`supabase functions deploy turn-credentials`), and checks the session itself too.

Support calls (`0105`) carry voice peer to peer over WebRTC, with the database as the signalling channel: `support_calls` rows ring (either side may call: `caller_role` 'admin' is an agent ringing a user, 'user' a user ringing support, where the first agent to answer is stamped `answered_by` by a conditional update), and `support_call_signals` carries the offer, answer and ICE candidates between the two people on a call only (RLS via `support_call_participant`), deleted when the call ends. A guard trigger keeps a non-admin client to ringing support as itself and moving the status of its own calls; `supabase/tests/support_call_audio.sql` covers it.

**Store releases.** `ios-release` and `android-release` (shared code in `supabase/functions/_shared/release.ts` + `release_handler.ts`, decisions unit-tested in `release_test.ts` with `deno test`) start App Store / Google Play builds of the **Flutter** app, which ships on both stores as `com.taxxee.teksi` (the identity this Expo app used, so the Flutter build replaces it in those listings; Expo's EAS builds no longer go to the stores). They dispatch `.github/workflows/{ios,android}-release.yml` in `getgroupmy/get-ride` with a GitHub token held in the function secrets (`GITHUB_RELEASE_TOKEN`, optional `GITHUB_RELEASE_REPOSITORY` / `GITHUB_RELEASE_REF`). The caller's session is verified and checked with `admin_can_edit` / `admin_can_read` on the page key `admin-settings-app-release` before anything reaches GitHub; a missing token answers 503 "not set up yet". The console is Admin → Settings → App Release (`app/admin-settings-app-release.tsx`, IO and pure helpers in `utils/storeReleaseStore.ts`); the Flutter admin has the same screen over the same functions. Signing secrets, version-number offsets and setup live in get-ride's `docs/store-release.md`.

RLS is enabled everywhere and — since migration `0069` — scoped rather than permissive. The central helper is `caller_is_admin()` (true for direct DB sessions, the service role, and profiles holding an `admin_access` row):

- **`ride_requests`** is participant-scoped: open requests are readable by everyone (the partner queue needs them), everything else is rider/partner/admin only. Riders insert rows carrying their own `auth.uid()`; partners claim/offer on open rows but must stamp `partner_id = auth.uid()` in the same update; `rider_id` is immutable after insert (trigger). Consequence: writes require an authenticated Supabase session — `rideRequestsStore.ts` surfaces `isPermissionDeniedError` / `RIDE_SIGN_IN_MESSAGE` for legacy local-PIN sessions, and partners no longer receive realtime UPDATEs for requests claimed by someone else (stale incoming cards self-dismiss on their countdown; the `status = 'open'` claim guard keeps the accept race safe).
- **Admin-managed config tables** (geo tables, settings, branding, commission/coin settings, IP rules, insurance/EV catalogs, …) keep public reads; writes are admin-only.
- **Personal/PII tables** (`emergency_contacts`, `user_sessions`, `user_location_history`, `voice_protection_recordings`, `support_*`, `provider_documents`, `vehicle`/`vehicle_documents`/assignments, `fare_ai_responses`) are owner-or-admin scoped. Push tokens are admin-only at the table level; devices register via the `push_register_token`/`push_unregister_token` RPCs (`adminSync.ts` falls back to the legacy direct writes on pre-`0069` databases). The support-agent roster comes from the `support_agents` RPC (same fallback pattern in `supportStore.ts`).
- **`admin_access`** writes require sub-admin edit access (the `0010` public-write policies are gone). First-run bootstrap: the `admin_access_bootstrap()` RPC makes the first authenticated caller the `'*'` admin on an empty table — the sub-admin screen retries through it automatically. Signed-in callers only since `0103`; signed-out callers always got `false`.
- **Service-role-only definer functions** (`0103`): `fare_ai_record_usage` (written by the `ai-route-proxy` edge function; it has no caller check, so a client could put every AI fare key on cooldown) and `expire_documents_daily` (run by pg_cron as `postgres`). Neither is callable by `anon` or `authenticated`.
- From `0066`: the wallet tables are read-only to clients (writes go through owner-scoped RPCs — see Wallets above), and the `app_settings` row `fare_ai_provider` (secret AI provider keys) is only visible to profiles with an `admin_access` row or the service role — non-admin clients get fare estimates through the `ai-route-proxy` edge function instead.
- From `00891`: **`wallet_transfer_requests`** (P2P GET.coin transfer handshake, `0065`) is participant-scoped: a row is readable only by its sender (`from_user_id`), its recipient (`to_user_id`) or `caller_is_admin()`, and `anon` has no select grant; since `0097` neither `anon` nor `authenticated` holds any write grant on it (insert/update/delete/truncate/references/trigger). Writes stay in the SECURITY DEFINER RPCs (`wallet_request_coin_transfer`, `wallet_respond_coin_transfer`, `wallet_cancel_transfer_request`). Realtime postgres_changes applies the same policy per subscriber, so the recipient popup (`to_user_id=eq.<uid>`) and the sender's watch (`id=eq.<id>`) in `transferRequestsStore.ts` (and the Flutter equivalents) keep working; the admin fraud scans read all rows as admins.
- Storage: buckets stay public (existing `getPublicUrl` links keep rendering) but the broad per-bucket SELECT (listing) policies are dropped and writes are admin- or owner-scoped; `voice-protection` objects are readable only by their owner's folder or admins (signed URLs). Since `0095`, non-admin writes to `avatars` and `ID_Image` (insert, update, delete) must be under a top-level folder named after the caller's auth uid (`<uid>/…`), so one user can no longer replace or delete another's profile photo or IC photo; admins keep full write access, and files already stored under the old `<country>/…` folders stay readable.
- From `0080`: **`ev_orders`** is the one *owner-scoped* settings category. TEKSI EV orders are created by the customer (see EV order flow below), so they cannot live in the admin-write-only `settings_entries`; they get their own table with the same `SettingEntry` shape plus `user_id` (defaulted from `auth.uid()`, frozen by trigger), readable/writable by owner-or-admin and deletable by admins only. `adminSync.ts` routes the category through `OWNER_SCOPED_CATEGORY_TABLE_MAP` and falls back to `settings_entries` when the table is missing (`isMissingTableError`); `AdminDataContext` keeps local-only rows of these categories across a remote fetch and retries their upsert, so an order created offline is never dropped.

Owner-scoped tables (like `profiles`) require `auth.uid()` to match the row; admin/back-office writes otherwise use the `service_role` key.

`profiles` (migration `0087`) adds admin UPDATE/DELETE policies (`caller_is_admin()`) and a protected-column guard. The `trg_profiles_a_guard` BEFORE UPDATE trigger rejects any non-admin *client* request (role `anon`/`authenticated`) that changes `id`, `phone`, `status`, `profile_status`, `id_verified`, `id_expiry_date`, `documents_ok`, `total_rides`, `display_id`, `referral_code`, `device_count`, `joined_at`, `created_at`, `pin_hash`, `pin_failed_attempts`, `pin_locked_until` or `mcash_*`. It raises `PROFILE_PROTECTED_COLUMN:<column>` (SQLSTATE 42501). SECURITY DEFINER functions (`set_login_pin`, `verify_pin_for_login`, `clear_login_pin`, `expire_documents_daily`, the signup trigger) run as their owner and pass through. If a new user-facing flow needs to write one of those columns, do it in a SECURITY DEFINER RPC rather than widening the guard. `phone` itself follows Supabase Auth: a verified number change (`auth.updateUser({ phone })` then `verifyOtp` type `phone_change` — Expo `change-number.tsx`, Flutter `ChangePhoneScreen`) moves `auth.users.phone`, and the `on_auth_user_phone_changed` trigger (`sync_profile_phone`, migration `0092`) copies it onto the profile. Before it, the profile kept the old number, so `verify_pin_for_login` / `profile_phone_lookup` still answered for the old one. Users can still edit their own name, email, avatar_url/profile_image, nationality, ic, address, id_image, id_type, gender and birth_date, and the legacy `login_pin`/`pin` inputs.

Partners, vehicles and their documents follow the same pattern (migration `0088`); the guards apply only to non-admin client requests, so SECURITY DEFINER functions, the service role and admins pass:
- **`partners` (`trg_partners_a_guard`):** a self-inserted row must start `unapproved`, with permit `none`/`pending` and rating/total_rides 0. Partners can't change `id`, `auth_user_id`, `display_id`, `status`, `permit`, `rating`, `total_rides`, `joined_at` or `created_at`. `documents_ok` ("all compulsory documents uploaded") stays partner-controlled.
- **`vehicle` (`trg_vehicle_a_guard`):** same start state. `status`, `permit` and the ids are protected. `auth_user_id`/`owner_partner_id` can only be set from empty to the caller (or the caller's own partner row), which is how onboarding takes over an admin-added vehicle.
- **`provider_documents` / `vehicle_documents` (`*_a_guard`, before the `*_expiry` triggers):** a new row must be `Pending Review` with no reviewer fields. Owners can only clear `reviewer_notes`/`reviewed_at`, can only move `status` to `Pending Review`, and any change to the document itself (file, number, dates, type, issuer) automatically sends it back to `Pending Review`.
- **Ride claiming:** only an approved partner (`caller_is_approved_partner()`, meaning status `approved` or any `permit-*`) can set themselves as `partner_id` on a ride request, i.e. accept or bid. This is enforced by `trg_ride_requests_a_guard_claim` (`RIDE_CLAIM_REQUIRES_APPROVED_PARTNER`), because a policy alone can be bypassed through another permissive UPDATE policy's WITH CHECK.
- **`partners` reads:** only the owner and admins. Onboarding uses `claim_partner_by_phone()` (links an admin-pre-added row by the verified sign-in phone) and `partner_ic_for_my_vehicle(partner_id)` (owner IC for the verify-owner step, returned only to the owner, an assigned driver or an admin), each with a pre-`0088` fallback in `partnerOnboardingStore.ts` / `vehicleOnboardingStore.ts`.
- **The legacy `vehicles` table** is admin-only.

Vehicle sessions (migration `0091`): `claim_vehicle`, `release_vehicle` and `touch_vehicle_session` are authenticated-only and raise `not_authorized` (SQLSTATE 42501) when `p_user_id` is not `auth.uid()`, unless the caller is an admin. Always pass the signed-in user's own id. `vehicleAssignmentStore.claimVehicle` reports a refused caller (including a legacy local-PIN session with no Supabase auth) as reason `not_authorized`, and the pickers show `VEHICLE_SIGN_IN_MESSAGE` for it.

To bootstrap a new Supabase project (`setup.sh` applies `schema.sql` + `seed.sql`, and deploys edge functions if the Supabase CLI is on PATH):
```bash
export SUPABASE_DB_URL="postgres://postgres:PASSWORD@db.REF.supabase.co:5432/postgres"
./supabase/setup.sh                # creates schema + seeds + edge functions
./supabase/setup.sh --reset        # wipe, rebuild, reseed
./supabase/setup.sh --schema-only  # skip seed data
./supabase/setup.sh --no-functions # skip edge-function deploy
```

The user's 6-digit sign-in PIN is stored as a bcrypt hash in `profiles.pin_hash` (migration `0052`) — never in plaintext. The legacy `pin` and `login_pin` columns still exist as *write-only* compatibility inputs: a `BEFORE INSERT OR UPDATE` trigger (`hash_profile_pin`) hashes anything written to them and nulls the plaintext. The client sets/changes the PIN via the `set_login_pin` RPC and clears it via `clear_login_pin` (both `auth.uid()`-scoped); see `registerUser` in `AuthContext.tsx`, which falls back to the legacy column write on pre-`0052` databases. PIN verification for login goes through the `verify_pin_for_login` RPC, which is rate limited: 5 consecutive wrong attempts lock verification for 15 minutes and the RPC raises `PIN_LOCKED:<seconds-remaining>` while locked (parsed client-side by `parsePinLockSeconds` in `utils/pinLock.ts`).

## Ride dispatch

Real ride matching goes through the `ride_requests` table via `utils/rideRequestsStore.ts` (no context — plain async functions plus Supabase realtime subscriptions). A rider inserts an `open` request; online partners subscribe to open requests in realtime, accept one (claiming it), and progress it through `accepted` → `arrived` → `on_trip` → `completed` (or `cancelled`/`expired`; open requests expire after 7 minutes, `REQUEST_EXPIRY_MS`). The rider watches their own request row for status changes. A database trigger (migration `0051`, reworked in `0067`) fires the `send-push` edge function to notify the partner audience whenever a new open request is inserted: all push webhook triggers post through the shared `send_push_webhook` helper (`pg_net`), which needs two Supabase Vault secrets: `project_url` (set by hand: `select vault.create_secret('https://YOURREF.supabase.co', 'project_url');`) and `push_webhook_secret` (generated by migration `0128`; sent as the `x-push-secret` header). Without either the helper posts nothing. `send-push` is deployed `--no-verify-jwt` because the webhook has no user JWT, so it checks every caller itself (`_shared/push_auth.ts`): the `x-push-secret` header, checked against Vault by the service-role-only `push_webhook_secret_ok()` so the secret exists in one place and needs no function secret; a bearer that is the service-role key; or a signed-in admin's token (`caller_is_admin()`, asked with that token). Anything else gets 401 (no credentials, or a token PostgREST rejects) or 403 (signed in but not an admin) before the body is read. The old Vault `service_role_key` secret is no longer read. Rotate the webhook secret with `select vault.update_secret(id, encode(extensions.gen_random_bytes(32), 'hex')) from vault.secrets where name = 'push_webhook_secret';`. Nothing else needs to change, because the database and the function both read it from Vault. Clients that called `send-push` themselves for a new or raised-fare request now get 403. The trigger already sends those pushes.

Additional dispatch behaviors, all riding on `ride_requests` columns:

- **Fare offers/bidding**: one bid stands at a time on the request row itself. A partner counter-offers via `submitRideOffer` (stamps `offered_fare` + their partner fields, row stays `open`); the rider raises the fare via `raiseRideRequestFare` (sets `fare` *and* `ride_fare`, the column the trip is billed at, and clears the bid). The rider accepting a bid is `acceptRideOffer`: their own row moves to `accepted` with that partner, billed at the offer, matched on the exact `partner_id` and `offered_fare` shown so a replaced bid is never accepted; declining (or the bidder withdrawing / their 45 s lapsing) is `clearRideOffer`. The bidder reads the result off the row with the pure `rideOfferOutcome` (won / outbid / raised / declined / closed) — before this the accept only opened the tracking screen and the partner never learned they had won. The Flutter app (get-ride `core/ride_bidding.dart`) writes the same contract, so the two can bid against each other.
- **Cancellation**: before the trip starts the rider cancels directly (`cancelRideRequest`, storing `cancel_reason`). Once `on_trip`, tapping X only *requests* cancellation (`cancel_requested_at`/`cancel_requested_by`, migration `0053`) — the driver sees a popup and accepts (→ `cancelled`) or declines (timestamp cleared).
- **Live location**: during an active ride both sides publish their real GPS position onto the request row (`publishLiveLocation` → `partner_live_*` / `user_live_*` columns, migration `0055`) and each side moves the other's map marker from realtime row updates.
- **Restore after restart**: on cold launch the rider is returned to their in-progress screen via `fetchOngoingRequestForRider` + `utils/ongoingRequestRestore.ts` (`buildRestoreTarget` maps status → `/ride-tracking` or `/ride-confirm`); the partner side uses `fetchOngoingRequestForPartner` to return to `/ride-running`.
- **Commission**: when a partner completes a trip, `ride-running.tsx` calls `chargeRideCommission` (see Wallets below).

## Wallets & commission

Each account has three wallets (`utils/walletStore.ts`, tables `wallets`/`wallet_transactions` from migration `0056`, rider-facing screen `app/wallet.tsx`):

- **GET.wallet** (`get_wallet`) — master wallet, used in both user and partner mode. Must stay non-negative. No payment gateway is wired up yet (the gateway settings are labels only), so since migration `0096` `wallet_topup` is admin/service-role only and a self-service reload gets `topup_requires_payment` (`TOPUP_UNAVAILABLE_ERROR` in `walletStore.ts`); before it, any signed-in account could credit itself up to RM100,000. A real gateway should credit through an edge function with the service role after verifying the payment.
- **GET.credit** (`get_credit`) — partner-only wallet that pays for in-app services and ride commissions; recharged by transferring from GET.wallet. May go negative (commission owed).
- **GET.coin** (`get_coin`, migrations `0061`–`0065`) — reward coin denominated in GC, used in both modes; must stay non-negative. The GC↔RM rate (and optional market-speculated pricing/supply cap) is set from Admin → Settings → Get Coin (`utils/getCoinStore.ts`). Coins are earned as ride rewards (`wallet_award_ride_coins` RPC, idempotent per ride), redeemed against QR payments and fares, bought/sold against GET.wallet on `app/wallet-trade.tsx`, and earned by both sides of a referral (`apply_referral`, migration `0078`; since `0094` only for an account created within the last 7 days — older accounts get `not_new_account` — and the 8-character account-id code must be given in full), sent P2P between accounts with recipient approval (migration `0065`, `utils/transferRequestsStore.ts`): the sender's confirm creates a pending `wallet_transfer_requests` row (`wallet_request_coin_transfer` RPC, recipients resolved by account id or phone server-side; since migration `0090` the sender only ever gets the recipient's name masked by `wallet_mask_name` — "Ahmad A." — in the RPC result, the row's `to_name`, their ledger memo and the accepted/declined push, so a phone number can't be mapped to a full account name; `0090` also masked the names already stored on old request rows and sender memos), the recipient gets a push + in-app popup (`components/IncomingTransferPopup.tsx`, mounted in `_layout.tsx`) naming the sender and amount, and the coins move 1:1 without minting only when they accept (`wallet_respond_coin_transfer` RPC); requests expire after 15 minutes, and on pre-`0065` databases the store falls back to the instant `wallet_transfer_coins` RPC (migration `0064`). Balances are ledger-driven: `wallet_transactions` rows drive `wallets.balance` via the `0060` trigger.

**Wallet security (migration `0066`)**: clients can only *read* `wallets`/`wallet_transactions` — every balance-changing operation goes through an owner-scoped `SECURITY DEFINER` RPC that asserts `auth.uid()` matches the wallet owner (`wallet_assert_caller`). QR payments use `wallet_pay`, coin trading uses `wallet_trade_coins` (rate decided entirely server-side by `get_coin_trade_quote()` since migration `0089`: buys at max(market, peg), sells at min(market, peg), so no sequence of trades can make RM; the client's `p_rate_per_gc` is ignored; supply cap enforced; regression test `supabase/tests/coin_trade_round_trip.sql`. `app/wallet-trade.tsx` shows both prices from that RPC via `fetchCoinTradeQuote`, falling back to `tradeQuoteFromMarket` (same rule) on older databases, and totals with `tradeAmount`, which rounds like the server), and fare coin redemption uses `wallet_redeem_fare_coins` (idempotent per ride via `ride_requests.fare_coins_redeemed_at`). `wallet_award_ride_coins` additionally requires the caller to be the ride's rider and the ride to be `completed`, and since migration `0093` prices the reward on the ride's stored fare (`ride_fare`, else `fare`) — its `p_fare` argument is ignored, because a client-supplied fare let a rider claim any ride's reward on RM10,000; `wallet_charge_ride_commission` requires the ride's partner and ignores client-supplied rates (always resolved server-side). On pre-`0066` databases `walletStore.ts` falls back to the old direct ledger inserts; when the database rejects the caller (`not_authorized`, e.g. a legacy local-PIN session) the store surfaces a sign-in prompt instead of failing generically.

On trip completion the platform commission is deducted from GET.credit through the `wallet_charge_ride_commission` RPC (migration `0057`) — atomic and idempotent (the charge is stamped on the ride row via `commission_charged_at`, so it can never apply twice).

Commission *rates* are configurable from Admin → Settings → Commission Rates (`app/admin-settings-commission.tsx`, `utils/commissionStore.ts`, table `commission_rates` from migration `0058`): one master platform default plus overrides resolved in priority order user → suburb → city → state → country → master → hardcoded 15% (`DEFAULT_COMMISSION_RATE`).

Both stores degrade gracefully: if the wallet/commission tables aren't in the live database yet, they fall back to device-local AsyncStorage copies and report `source: "local"` so callers can surface a notice.
